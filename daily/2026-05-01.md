## Agent 重点进展

### 1. OpenAI 正在把内部 Codex 工作方式外溢成可复用的 Agent 基础设施

- 发生了什么：OpenAI 在 2026-04-15 发布新版 Agents SDK，核心是 model-native harness、native sandbox execution，以及对 memory、MCP、skills、AGENTS.md、shell 和文件编辑等原语的标准化支持；随后在 2026-04-27 开源 Symphony，把项目管理板变成 coding agents 的 control plane。来源：[OpenAI Agents SDK](https://openai.com/index/the-next-evolution-of-the-agents-sdk/) [OpenAI Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/) [Harness engineering](https://openai.com/index/harness-engineering/)
- 为什么重要：这说明 OpenAI 的重心不再只是“提供一个能写代码的模型”，而是在输出一整套 agent runtime 与 orchestration 设计。对于开发者和团队来说，价值不只是更强的单次完成率，而是把 agent 作为持续协作者接进软件流程。
- 我的解读：OpenAI 正在把“Codex 怎样工作”变成“开发者怎样搭自己的 agent 系统”。如果这条线继续推进，未来大家比较的会是 SDK 的运行时设计、任务控制面、review 流，而不只是模型分数。
- 值得继续追踪什么：一是 Symphony 是否快速出现对 Linear/Jira/GitHub 的第三方适配；二是 Codex CLI、App Server、Agents SDK 会不会进一步统一成同一套 substrate；三是 OpenAI 是否继续把内部 harness 经验公开出来。来源：[Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/) [OpenAI Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/)

### 2. Cursor 正在从 AI IDE 继续演化为可编程的 Agent Runtime

- 发生了什么：Cursor 在 2026-04-29 推出 public beta 的 Cursor SDK，允许开发者直接调用和 Cursor 桌面端、CLI、Web 相同的 runtime、harness 与模型；同次更新还把 Cloud Agents API 改成 durable agent + per-run streaming 的结构，并补了 archive / unarchive / delete 等生命周期控制。再往前一周，Cursor 3.2 把 async subagents、worktrees、多根工作区带进主界面。来源：[Cursor Changelog](https://cursor.com/changelog) [Cursor SDK announcement](https://cursor.com/changelog) [Latent Space: Cursor's Third Era](https://www.latent.space/p/cursor-third-era/)
- 为什么重要：Cursor 的边界已经明显超出“编辑器里的智能补全”。它在提供的不是一个 IDE feature，而是一套可在本地和云端复用的 agent runtime，背后还连着 GitHub handoff、远程执行、可编排 API。
- 我的解读：Cursor 的竞争单位正在从“最好用的 AI 编辑器”变成“最顺手的开发工作流后端”。这会让它和纯 IDE、纯 coding agent、纯 hosted automation 三类产品都发生重叠。
- 值得继续追踪什么：一是 SDK 生态会不会迅速长出内部开发平台和团队自动化的案例；二是 durable cloud agents 是否进一步走向自托管或 VPC 化；三是 Cursor 如何平衡本地开发体验与 hosted runtime 的商业模式。来源：[Cursor Background Agents](https://docs.cursor.com/en/background-agents) [Cursor GitHub integration](https://docs.cursor.com/en/github)

### 3. Anthropic 正在同时强化“终端前台”和“托管后台”：Claude Code 与 Managed Agents 两条线开始合流

- 发生了什么：Anthropic 在 2026-04-08 发布《Scaling Managed Agents: Decoupling the brain from the hands》，明确把 session、harness、sandbox 拆成稳定接口；Claude Code 的 2026-04-20 至 2026-04-24 周更则推出 `/ultrareview` 研究预览、automatic session recaps、forked subagents、web 端重构；更早一点的 2.1.108 changelog 还加入了 1 小时 prompt cache TTL 和基于 Skill tool 的 slash command discoverability。与此同时，Claude Opus 4.7 在 2026-04-16 上线，突出 1M context、长程 coding 与 agent workflow。来源：[Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents) [Claude Code Week 17](https://code.claude.com/docs/en/whats-new/2026-w17) [Claude Code Changelog](https://code.claude.com/docs/en/changelog) [Claude Opus 4.7](https://www.anthropic.com/claude/opus)
- 为什么重要：这是非常少见的“双向验证”路径。一边是开发者能直接感知的 Claude Code feature，一边是平台层更抽象的托管 agent 接口；两边都在解决长任务、持续会话、上下文恢复、云端验证这些同一个问题族。
- 我的解读：Anthropic 目前最值得重视的不是某一个单点 feature，而是它对 long-running agent 的系统工程投入非常深。它不是简单地把“更聪明的模型”放进终端，而是在把 agent 做成一种可持续运行、可托管、可恢复的工作系统。
- 值得继续追踪什么：一是 `/ultrareview` 这种云端 bug-hunting fleet 会不会成为合并前标准动作；二是 Managed Agents 是否继续开放更明确的平台接口；三是 Anthropic 如何处理 subscription、API 和第三方 harness 之间的经济边界。辅助视角可看：[Anthropic at Google Cloud Next 2026](https://www.anthropic.com/events/anthropic-at-google-cloud-next-2026) [Get Good at Agents](https://www.interconnects.ai/p/get-good-at-agents?action=share%5C%5C%5C) [Claude Code and What Comes Next](https://www.oneusefulthing.org/p/claude-code-and-what-comes-next?action=share)

### 4. Hermes 正在从“有记忆的个人助手”升级成“可长期运行的多 Agent 操作系统”

- 发生了什么：Hermes 最新公开 release `v0.10.0 (v2026.4.16)` 把 Tool Gateway 做成正式能力，让 Nous Portal 订阅直接获得 web search、image generation、TTS、browser automation；文档层面，Hermes 继续把 persistent memory、context files、cron、subagent delegation 放在核心能力区，而今天最值得注意的是 Kanban 文档已经把“durable multi-agent profile collaboration”讲得很具体，包括共享任务数据库、命名 worker、handoff comment、retry / unblock、scratch / worktree 工作空间。来源：[Hermes v0.10.0 release](https://github.com/NousResearch/hermes-agent/blob/main/RELEASE_v0.10.0.md) [Hermes Features](https://hermes-agent.nousresearch.com/docs/user-guide/features/overview/) [Hermes Kanban](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban)
- 为什么重要：Hermes 的重点已经不是“会不会调用更多工具”，而是“长期运行时怎样保留 identity、memory、handoff、schedule、workspace”。这正是当前很多 Agent 产品还缺的中后台层。
- 我的解读：如果说 Cursor 和 Claude Code 在把 agent 做成高效的开发生产力工具，Hermes 更像是在摸索“长寿命 Agent OS”的形状。对于研究助理、个人运营助理、长期 coding copilot 这类场景，这条路线会很有价值。
- 值得继续追踪什么：一是 Kanban 是否能成为比 in-process subagent 更稳定的多 agent 协作范式；二是 Tool Gateway 与第三方 provider 的稳定性；三是 Hermes 在 ACP / MCP / IDE 方向的互操作进展。来源：[Hermes Delegation](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation) [Hermes Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/) [Hermes Tool Gateway](https://hermes-agent.nousresearch.com/docs/user-guide/features/tool-gateway)

### 5. OpenClaw 继续稳固自己作为“连接层 / 兼容层 / 运行时胶水层”的位置

- 发生了什么：OpenClaw 文档现在已经把 `openclaw mcp serve` 的双重角色讲清楚了: 一方面它可以作为 MCP server 暴露给 Codex、Claude Code 等客户端，另一方面它又能维护 OpenClaw 自己要消费的 outbound MCP server registry；技能系统也明确了从 `<workspace>/skills` 到 `~/.openclaw/skills` 再到 bundled skills 的优先级。发布节奏上，官方 release policy 写明 beta-first；GitHub 上可见 `2026.4.14` 包在最近几天发布，而 `2026.4.1` 版本加入了 `/tasks` 作为当前会话的 chat-native background task board，并继续强化 ACP / Responses / plugin registry 相关能力。来源：[OpenClaw MCP](https://docs.openclaw.ai/cli/mcp) [OpenClaw Skills](https://docs.openclaw.ai/tools/skills) [OpenClaw Release Policy](https://docs.openclaw.ai/reference/RELEASING) [OpenClaw Releases](https://github.com/openclaw/openclaw/releases) [OpenClaw package versions](https://github.com/orgs/openclaw/packages/container/openclaw/versions)
- 为什么重要：OpenClaw 的核心价值不是某一个模型效果，而是跨模型、跨通道、跨 agent client 的连接能力。随着大家都在做自己的 hosted runtime，这种“把现有会话、工具、插件、渠道桥接起来”的层反而更有结构性价值。
- 我的解读：OpenClaw 更像 Agent 时代的 compatibility / connectivity layer。尤其当前行业正在形成 MCP、skills、ACP、channel routing 等多层协议面时，谁能做稳定桥接，谁就容易获得生态位置。
- 值得继续追踪什么：一是 `/tasks` 会不会继续演化成更完整的编排层；二是 plugin registry 与 security hardening 的成熟度；三是第三方模型订阅与第三方 harness 的关系变化会不会反过来推高这类中间层的需求。媒体侧信号可参考：[Anthropic tells OpenClaw users to pay up](https://www.therundown.ai/p/anthropic-tells-openclaw-users-to-pay-up) [No Claude for Claws](https://www.bensbites.com/p/no-claude-for-claws?publication_id=4379299&r=5dj1m5)

### 6. 评测、企业数据与方法论，开始一起把长任务 Agent 讲清楚

- 发生了什么：FrontierSWE 在 2026-04 发布首批 17 个 ultra-long-horizon engineering tasks，专门评测需要新想法、长规划、复杂实现的技术任务；Anthropic 与 Material 的《2026 State of AI Agents Report》则显示，57% 的组织已把 agent 用于 multi-stage workflow，86% 的组织已把 coding agents 推到“超出实验”阶段；与此同时，4 月两篇 Context Engineering 预印本开始尝试把“上下文装配”正式化。来源：[FrontierSWE](https://www.frontierswe.com/blog) [The 2026 State of AI Agents Report](https://resources.anthropic.com/hubfs/The%202026%20State%20of%20AI%20Agents%20Report.pdf) [Context Engineering 2603.09619](https://arxiv.org/abs/2603.09619) [Context Engineering 2604.04258](https://arxiv.org/abs/2604.04258)
- 为什么重要：这意味着行业终于不只是在“展示 demo”，也开始建立更像样的评估与讨论框架。公开 benchmark、企业 adoption 数据、方法论语言三者一起出现，才有可能真正比较不同 agent 系统。
- 我的解读：现在的部署速度已经跑在理论前面，但理论和评测正在补上。未来半年最值得看的，不只是哪个模型又涨了几分，而是谁先把长任务 benchmark、上下文工程、交接对象、回归评测做成体系。
- 值得继续追踪什么：一是公开 benchmark 是否从短 PR / 短命令进一步转向 8 小时以上任务；二是 context engineering 会不会从“好文章”演化为团队可操作的 checklist；三是企业 adoption 数据能否进一步区分 hosted 与 self-hosted agent 的表现。来源：[Anthropic at Google Cloud Next 2026](https://www.anthropic.com/events/anthropic-at-google-cloud-next-2026) [TLDR Trends: March 2026](https://advertise.tldr.tech/research/tldr-trends-march-2026/)

## 研究 / 工程趋势小结

- 趋势 1：Agent 正在 runtime 化。真正的差异点越来越不是单次回答，而是 session、sandbox、memory、workflow orchestration 怎么设计。来源：[OpenAI Agents SDK](https://openai.com/index/the-next-evolution-of-the-agents-sdk/) [Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents) [Cursor Changelog](https://cursor.com/changelog)
- 趋势 2：更大的 context window 仍然重要，但它已经不够。真正决定长任务体验的，是 recap、handoff、durable log、prompt caching、context transform、lazy-loaded skills 这些配套机制。来源：[Claude Code Changelog](https://code.claude.com/docs/en/changelog) [Claude Code Week 17](https://code.claude.com/docs/en/whats-new/2026-w17) [Hermes Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)
- 趋势 3：Multi-agent 正在从“泛化灵感”收缩为几个高价值形状：上下文隔离、并行执行、专门化验证、持久 handoff。谁还把 multi-agent 当成单纯角色扮演，很可能很快掉队。来源：[Anthropic at Google Cloud Next 2026](https://www.anthropic.com/events/anthropic-at-google-cloud-next-2026) [OpenAI Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/) [Hermes Kanban](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban)
- 趋势 4：协议层和技能层会成为生态壁垒。MCP、skills、AGENTS.md、context files、ACP 这些看似“外围”的东西，正在决定不同 agent 能不能真正接入团队环境。来源：[OpenClaw MCP](https://docs.openclaw.ai/cli/mcp) [OpenClaw Skills](https://docs.openclaw.ai/tools/skills) [OpenAI Agents SDK](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)
- 趋势 5：企业落地的瓶颈越来越清楚地指向 integration、data quality、change management，而不是“模型够不够聪明”。这意味着下一波竞争会更偏工程与组织能力。来源：[The 2026 State of AI Agents Report](https://resources.anthropic.com/hubfs/The%202026%20State%20of%20AI%20Agents%20Report.pdf)

## 对产品 / 业务设计的启发

- 先把 session log、handoff object、review loop 做扎实，再去追求更多 agent 角色和更多工具，通常更容易形成真实生产力。
- 要尽早明确自己站在哪种 runtime 位置上：是像 Cursor / OpenAI / Anthropic 那样偏 hosted automation，还是像 Hermes / OpenClaw 那样偏用户掌控、偏兼容桥接。这个选择会直接影响安全、定价、记忆策略与生态边界。
- 如果面向团队与企业，skills、context files、MCP config、task board、eval artifacts 最好都做成显式资产，而不是藏在不可见 prompt 里。2026 年的 Agent 产品差异，越来越体现在这些“中后台可治理性”上。
